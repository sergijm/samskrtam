## 2. Примечание об окончаниях для основ -i, -u, -ṛ

Для основ на **-i**, **-u**, **-ṛ** (`vowel_type`: I, I_LONG, U, U_LONG, R) падежные окончания **не различаются** по грамматическому роду ни в одном падеже/числе.
Подробнее см. [ADR-005: Единство окончаний для основ -i, -u, -ṛ независимо от рода](../conventions.md#adr-005-единство-окончаний-для-основ--i--u--ṛ-независимо-от-рода).

**Ключевые следствия:**
- Ключ агрегации прогресса остаётся `(gender, caseType, numberType)` для единообразия по всем 8 урокам склонений (включая declensions-i, declensions-u, declensions-r).
- `caseEnding` для MASCULINE и FEMININE в рамках одного (caseType, numberType) совпадает.
- `successRate` считается раздельно по роду, так как это разные основы/слова.

## 3. UI стартовой страницы квиза: сводная и подробная таблицы прогресса

**Статус: ЧЕРНОВИК (добавлено при постановке задачи Агентам 2/3/6).**

### 3.1. Две вкладки вместо одной таблицы

Текущая единственная таблица (колонки: Статус, Падеж, Число, Род, Окончание, Изучено) остаётся, но перемещается на вторую вкладку. Компонент — TabView с двумя вкладками:

1. **«По падежам»** — новая сводная таблица. Строка — один падеж (caseType), без разбиения по числу и роду. Колонки: Статус, Падеж, Изучено (агрегированный прогресс). Колонки Число/Род/Окончание в этой вкладке не показываются, так как они не имеют смысла для агрегата.
2. **«Подробно»** — существующая таблица без изменений (Статус, Падеж, Число, Род, Окончание, Изучено).

### 3.2. Агрегация прогресса по падежу

Значение «Изучено» на вкладке «По падежам» — агрегат всех строк подробной таблицы с этим caseType (по всем numberType и gender). Способ агрегации (среднее / доля выученных комбинаций/ min) определяет Агент 2 при реализации на основе уже существующей модели прогресса (см. §2 и `services/quiz-service.md`) и указывает выбор явно в реализации и в этом документе постфактум.

### 3.3. Клик по значению в колонке «Изучено» — переход в отфильтрованный квиз

На обеих вкладках значение в колонке «Изучено» становится кликабельным. По клику:

- Формируется фильтр вопросов: на вкладке «Подробно» — по конкретным (caseType, numberType, gender) выбранной строки; на вкладке «По падежам» — только по caseType (без ограничения по numberType/gender).
- Если для пользователя уже существует незавершённая (`IN_PROGRESS`) сессия квиза с точно таким же фильтром — квиз резюмируется (resume) с той же сессией, а не создаётся новая.
- Если незавершённой сессии с таким фильтром нет — стартует новая сессия квиза, содержащая только вопросы, отфильтрованные по этому критерию.
- Различие критерия фильтра (детальный vs по падежу) означает, что это разные сессии квиза — сессия, начатая с вкладки «По падежам» (без фильтра по числу/роду), не резюмируется кликом по детальной строке того же падежа, и наоборот.

### 3.4. Решения

**Признак типа фильтра в `QuizSession` — РЕШЕНО: явный маркер (вариант А).**

В `QuizSession` добавляются поля:
- `filterScope` — перечисление: `CASE_ONLY` (фильтр только по падежу, вкладка «По падежам») либо `CASE_NUMBER_GENDER` (детальный фильтр, вкладка «Подробно»).
- `filterCaseType` — падеж фильтра (обязателен всегда).
- `filterNumberType` — число фильтра (обязателен только при `filterScope = CASE_NUMBER_GENDER`, иначе null).
- `filterGender` — род фильтра (обязателен только при `filterScope = CASE_NUMBER_GENDER`, иначе null; для основ без родового различия — см. §2 — используется `UNSPECIFIED`, как и в остальной модели прогресса).

Поиск существующей незавершённой сессии для резюма выполняется прямым запросом по этим полям (`filterScope` + `filterCaseType` + при необходимости `filterNumberType`/`filterGender`), а не сравнением множества вопросов сессии — это отдельная миграция Flyway в схеме quiz-service, добавляемая к текущей структуре `QuizSession` (ответственность Агента 2), и отражается в OpenAPI при обновлении контракта старта квиза (ответственность Агента 6).

**Агрегация «Изучено» для сводной строки — открыт.** Способ агрегации (среднее / доля выученных комбинаций / min по вложенным numberType×gender) по-прежнему определяет Агент 2 при реализации и отражает здесь постфактум.
