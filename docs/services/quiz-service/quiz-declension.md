## 2. Примечание об окончаниях для основ -i, -u, -ṛ

Для основ на **-i**, **-u**, **-ṛ** (`vowel_type`: I, I_LONG, U, U_LONG, R) падежные окончания **не различаются** по грамматическому роду ни в одном падеже/числе.
Подробнее см. [ADR-005: Единство окончаний для основ -i, -u, -ṛ независимо от рода](../conventions.md#adr-005-единство-окончаний-для-основ--i--u--ṛ-независимо-от-рода).

**Ключевые следствия:**
- Ключ агрегации прогресса остаётся `(gender, caseType, numberType)` для единообразия по всем 8 урокам склонений (включая declensions-i, declensions-u, declensions-r).
- `caseEnding` для MASCULINE и FEMININE в рамках одного (caseType, numberType) совпадает.
- `successRate` считается раздельно по роду, так как это разные основы/слова.

**Местоимения (ADR-008) — тот же паттерн, без нового itemType:** уроки `pronouns-personal`/`pronouns-demonstrative`/`pronouns-interrogative`/`pronouns-relative`/`pronouns-reflexive` используют `DECLENSION_FORM` наравне с обычными основами. `pronouns-personal` (aham/tvam) — `gender = UNSPECIFIED`, как i/u/ṛ-основы выше. `pronouns-demonstrative`/`interrogative`/`relative` (tad/etad/idam/kim/yad) — по 3 стема на класс (MASCULINE/FEMININE/NEUTER), как a-основы одного рода (ADR-004). `pronouns-reflexive` (ātman) — обычная a-основа муж. рода, данные дублируют `declensions-a-masc` под отдельным slug (сознательный выбор, см. ADR-008). Энклитики и несклоняемое `svayam` — вне контракта DECLENSION_FORM в этой итерации.

Вместо неё — первая колонка с чекбоксом множественного выбора строк (`DataTable selectionMode="multiple"`).

### 3.2. Агрегация прогресса

Значение «Изучено» на вкладках «По падежам» и «По числам» — агрегат всех строк подробной таблицы с соответствующим caseType/numberType (по всем остальным измерениям). Способ агрегации (среднее / доля выученных комбинаций / min) — единый для обеих вкладок, определяет Агент 2 при реализации на основе уже существующей модели прогресса (см. §2 и `services/quiz-service.md`) и указывает выбор явно в реализации и в этом документе постфактум.

### 3.3. Мульти-выбор строк и запуск квиза

- Выбор чекбоксов независим для каждой из трёх вкладок прогресса (переключение вкладки не сбрасывает и не объединяет выбор с другой вкладкой).
- Кнопка **«Начать квиз»** запускает квиз только по комбинациям, соответствующим строкам, отмеченным чекбоксом **на активной в данный момент вкладке**. Если на активной вкладке не отмечена ни одна строка — берутся все строки этой вкладки (т.е. весь урок в рамках выбранного scope).
- На кнопке отображается динамический счётчик **N** — количество итоговых (caseType, numberType, gender)-комбинаций, которые войдут в квиз (т.е. развёрнутое произведение, а не число отмеченных строк): `Начать квиз ({N})`. Пересчитывается при каждом изменении выбора на активной вкладке.
  - На вкладке «Подробно» N — это просто количество выбранных строк (или всех строк вкладки, если выбор пуст) — там строка уже равна одной комбинации.
  - На вкладках «По падежам» и «По числам» строка агрегирует несколько измерений, поэтому N — это произведение: (кол-во выбранных падежей или, если ничего не выбрано — все 8 падежей) × (кол-во выбранных чисел или, если ничего не выбрано — все 3 числа: sg/du/pl) × (кол-во родов основы: 1 или 2, в зависимости от того, различает ли данный склоняемый тип род — см. §2). Например, для a-основы (различающей 2 рода: мужской/средний или мужской/женский в зависимости от урока) при выборе 3 чисел на вкладке «По числам» и незаданном выборе падежей: N = 8 падежей × 3 числа × 2 рода = 48.
  - Общая формула: N = |выбранные_падежи ∪ все_падежи, если пусто| × |выбранные_числа ∪ все_числа, если пусто| × |число_родов_основы|. Для основ без родового различия (см. §2, gender = UNSPECIFIED) множитель родов равен 1.
- При нажатии кнопки «Начать квиз» бэкенд сначала проверяет, существует ли у пользователя незавершённая (`IN_PROGRESS`) сессия по данному уроку с точно таким же фильтром — тем же `filterScope` и тем же множеством значений (`filterCaseTypes`/`filterNumberTypes`/`filterCombinations`, развёрнутым на момент старта, см. §3.4), сравнение множества — без учёта порядка:
  - **если существует** — квиз резюмируется (используется та же сессия, тот же прогресс по ответам, без создания новой);
  - **если не существует** — создаётся новая сессия квиза, содержащая только вопросы, отфильтрованные по этому критерию (N комбинаций из счётчика на кнопке).
- Клик по значению в колонке «Изучено» одной строки — частный случай того же механизма: эквивалентен выбору только этой одной строки на данной вкладке и немедленному запуску/резюму квиза по ней.

### 3.4. Решения

**Признак типа фильтра в `QuizSession` — РЕШЕНО: явный маркер + множество значений.**

В `QuizSession` добавляются поля:
- `filterScope` — перечисление: `CASE_ONLY` (вкладка «По падежам»), `NUMBER_ONLY` (вкладка «По числам»), `CASE_NUMBER_GENDER` (вкладка «Подробно»).
- `filterCaseTypes` — множество падежей фильтра (непусто при `CASE_ONLY`; пусто/не используется при других scope).
- `filterNumberTypes` — множество чисел фильтра (непусто при `NUMBER_ONLY`; пусто/не используется при других scope).
- `filterCombinations` — множество троек (caseType, numberType, gender) фильтра (непусто при `CASE_NUMBER_GENDER`; для основ без родового различия — см. §2 — используется `UNSPECIFIED`, как и в остальной модели прогресса).

Формат хранения множеств (JSON-массив в отдельной колонке vs связанная таблица `quiz_session_filter_items`) определяет Агент 2 при реализации миграции Flyway и указывает выбор постфактум. Пустое множество при старте сессии (ни один чекбокс не выбран) разворачивается на бэкенде в полный набор значений соответствующего scope на момент старта — сохраняется именно развёрнутый набор, а не признак «выбрано всё», чтобы резюм-сравнение оставалось простым сравнением множеств.

Поиск существующей незавершённой сессии для резюма выполняется по равенству (`filterScope` + соответствующее множество, сравнение без учёта порядка) — это отдельная миграция Flyway в схеме quiz-service (ответственность Агента 2), отражается в OpenAPI при обновлении контракта старта квиза (ответственность Агента 6, см. `docs/openapi/quiz/parameters.yaml` и `quiz-sessions.yaml`).

**ИЗМЕНЕНО:** сам алгоритм пре-фильтрации вопросов по `filterScope`/множеству (ранее —
`SessionCreationService.applyScopeFilter` в quiz-service, применявшийся к уже полученному от
content-service списку `generatedQuestions[]`) перенесён в content-service — см.
`content-service.md` (раздел «Внутреннее API для quiz-service»). quiz-service лишь:
1) хранит `filterScope`/множество в `QuizSession` (как описано выше, для резюма);
2) прокидывает те же значения как query-параметры в `ContentClient.generateQuizData(...)`;
3) получает от content-service уже отфильтрованный список и, если он пуст, отвечает
   `SCOPE_FILTER_EMPTY` — эта проверка остаётся в quiz-service, так как это бизнес-ошибка
   сессии, а не content-service.
   Причина переноса: `generate-quiz-data` — единственная точка генерации вопросов, и фильтрация
   по грамматическим признакам вопроса логически относится к домену контента, а не к домену
   сессий квиза.

## 4. Типы вопросов (`questionType`)

**Статус: ЧЕРНОВИК.**

До этого раздела квиз склонений поддерживал единственный неявный тип вопроса. Ниже — три типа под общим полем `QuestionDto.questionType` (см. `openapi/quiz/schemas/session.yaml`). Смена типа вопроса — исключительно решение модуля рендеринга; она не меняет генератор отбора (`quiz-generator-spec.md` §3–4), не заводит новый `itemType` и не меняет модель `quiz_item_score` — `externalRefId` для всех трёх типов остаётся тем же `case_endings.id` (§2.1 `quiz-generator-spec.md`).

### 4.1. FORM_BY_CASE (существующий, по умолчанию)

Дано: основа (`stem`, деванагари, перевод) + падеж/число/род. Нужно выбрать правильную словоформу среди дистракторов-форм (`optionType=FORM`). Без изменений относительно текущей реализации — описан здесь только для полноты перечисления типов.

### 4.2. CASE_BY_FORM (обратная задача)

Дано: готовая словоформа той же основы (`formIast`/`formDevanagari` на уровне вопроса — не основа и не падеж). Нужно выбрать правильную тройку (падеж, число, род) среди дистракторов-комбинаций (`optionType=CASE_COMBINATION`).

**Генерация дистракторов:** правильная тройка — та, что породила данную словоформу. Дистракторы — другие тройки (caseType, numberType, gender) **этого же vowel_type**, при этом приоритет отдаётся тройкам, чьё окончание **графически совпадает или близко** к правильному (например nom./voc./acc. sg. среднего рода — классический источник омонимии) — иначе задача вырождается в угадывание по чтению. Итоговый набор: 1 верная + 3 неверных тройки (как и в FORM_BY_CASE), минимум 1 из дистракторов должен быть омонимом при наличии такового у данной основы/vowel_type, остальные — случайные тройки того же vowel_type.

**Особый случай:** для vowel_type I/I_LONG/U/U_LONG/R (ADR-005, §2 этого документа) варианты-дистракторы всегда содержат `gender: UNSPECIFIED`; сама тройка не варьирует род, только caseType/numberType.

**Локализация вариантов:** каждый `CASE_COMBINATION`-option обязан нести `caseRu/caseEn/numberRu/numberEn/genderRu/genderEn` — переиспользуются те же справочники, что и в `grammar.yaml#GrammarQuestionProgress` (не заводить второй источник переводов падежей).

**BUGFIX (текст объяснения):** `GeneratedQuizQuestionDto.explanationRu/explanationEn` для `CASE_BY_FORM` **не должен** переиспользовать текст FORM_BY_CASE ("Правильная форма для основы '%s' в падеже '%s' и числе '%s' — '%s'"), поскольку в CASE_BY_FORM форма уже дана в условии, а угадывается падеж/число. Формулировка должна описывать обратную связь: для формы `correctFormIast` основы `stem` правильный ответ — падеж `targetCase`/число `targetNumber` (+ род, если применимо). Пример RU: «Форма 'daivam' основы 'daiva-' стоит в падеже 'Именительный', числе 'Единственное'». Формируется в `DeclensionQuizGeneratorService.generateSingleQuestion(...)` веткой по `questionType` (после назначения `questionType`, т.к. текст зависит от него); для `ENDING_MATCH` аналогично — объяснение должно говорить об окончании и всех тройках, которым оно соответствует, а не о конкретной форме.

**BUGFIX (проверка ответа):** для `CASE_BY_FORM` сравнение `selectedFormIast == correctFormIast` в `SessionOperationsService.processAndSaveAnswer` **некорректно**, т.к. `correctFormIast` вопроса — это форма, данная в условии, а не идентификатор выбранного варианта; вдобавок допустимый омоним-дистрактор (§4.2 выше) может иметь тот же `formIast`, что и правильная тройка, из-за чего заведомо неверный вариант засчитается как верный при простом сравнении строк формы. Корректность для `CASE_BY_FORM` должна определяться сравнением выбранной тройки (`caseType`+`numberType`+`gender` выбранного `CASE_COMBINATION`-option) с тройкой `targetCase`/`targetNumber`/`gender` вопроса, а не сравнением текста формы. Аналогично для `ENDING_MATCH` — сравнение множеств троек (см. §4.3, «Оценка ответа»), а не текста.

### 4.3. ENDING_MATCH (омонимия окончаний, multi-select)

Дано: голое окончание в IAST (`caseEnding`, например `au`), **без основы** — вопрос сознательно оторван от конкретного слова, чтобы проверять знание системы окончаний, а не запоминание конкретной парадигмы. Нужно выбрать **все** тройки (падеж, число, род), которым соответствует это окончание, из смешанного пула правильных и неправильных троек.

**Мотивация типа:** прямо тренирует омонимию, упомянутую в §2 (ADR-005) и в целом свойственную санскритской системе окончаний (напр. `au` = N/V/Ac du. во многих родах и типах основ одновременно).

**Формирование пула вариантов:**
- Все тройки (caseType, numberType, gender) данного vowel_type, чьё `caseEnding` совпадает с вопросным — все они верны и все включаются в пул (без выборочного отбрасывания корректных вариантов — иначе `caseEnding` перестаёт быть однозначно определён внутри вопроса).
- Дистракторы добираются из троек с **другим** окончанием того же vowel_type до достижения целевого размера пула. Целевой размер пула — 5–7 вариантов (меньше, чем количество верных + минимум 2 дистрактора, если верных троек мало; конкретную формулу и константу определяет Агент 2 при реализации, аналогично `maxNewPerSession` и другим константам генератора).
- Пул не обязан быть кратен количеству верных ответов — важно только, что каждая верная тройка встречается ровно один раз.

**Оценка ответа:** см. `answers.yaml#AnswerRequest/AnswerResponse` — точное совпадение множеств (`selectedOptionIds` == множество всех верных `id`), без частичного зачёта. Обоснование отсутствия partial credit: формула score (§2.5 `quiz-generator-spec.md`) рассчитана на бинарный результат правильно/неправильно на один `QuizItem`; частичный зачёт потребовал бы отдельной ветки формулы только для этого questionType, что нарушает инвариантность генератора (§5 `quiz-generator-spec.md`).

**Открытый вопрос:** если у окончания в рамках vowel_type всего одна верная тройка (нет омонимии) — включать ли такое окончание в пул ENDING_MATCH вообще, или исключать при выборе `QuizItem` для этого questionType на этапе рендеринга (вопрос тогда неотличим от банального CASE_BY_FORM с одним верным ответом). Решает Агент 2 совместно с Агентом 6 при реализации; временное решение — исключать (генерировать ENDING_MATCH только для окончаний с ≥2 верными тройками).

### 4.5. Перемешивание типов в рамках одной сессии

**Статус: ЧЕРНОВИК.**

Требование: в одном квизе вопросы разных `questionType` должны чередоваться, а не идти блоками/константным типом на весь квиз.

**Где происходит выбор типа:** в content-service, в момент построения каждого `GeneratedQuizQuestionDto` (т.е. **до** того, как quiz-service вызывает `DeclensionOptionGeneratorService`). Это сохраняет инвариант §5 `quiz-generator-spec.md`: алгоритм отбора `QuizItem` (какую основу/падеж/число включить в сессию) остаётся полностью независим от того, как этот item потом отрендерится — `questionType` не влияет на выбор item, только на способ его подачи.

**Алгоритм назначения (на каждый DECLENSION_FORM-вопрос независимо):**
1. Базовые веса: `FORM_BY_CASE = 0.5`, `CASE_BY_FORM = 0.3`, `ENDING_MATCH = 0.2`.
2. Если для выбранной тройки (stem, case, number) окончание имеет **менее 2** омонимичных троек (условие §4.3, шаг 2.4/3) — вес `ENDING_MATCH` обнуляется, его 0.2 добавляется к `CASE_BY_FORM` (итого `FORM_BY_CASE=0.5 / CASE_BY_FORM=0.5`).
3. Anti-repeat правило: если два предыдущих вопроса **в этой сессии** (по `questionNumber - 1` и `questionNumber - 2`) уже имели один и тот же `questionType`, этот тип временно исключается из розыгрыша для текущего вопроса (веса оставшихся типов перенормируются). Для `questionNumber <= 2` правило не применяется (недостаточно истории).
4. Бросок — обычный взвешенный `Random` (детерминированный seed не требуется — воспроизводимость сессии обеспечивается персистентностью результата, см. ниже, а не повторяемостью генератора).
5. Для `questionSource=VOCABULARY` (лексические вопросы) `questionType` не назначается вообще — там остаётся текущее поведение без изменений; шаги 1–4 применяются только когда `itemType=DECLENSION_FORM`.

**Персистентность:** результат розыгрыша должен быть детерминирован **в рамках одной сессии** при resume/перезагрузке страницы — иначе тип вопроса будет "прыгать" между заходами. Поэтому `questionType` вычисляется один раз при первичной генерации сессии (`session_questions` создаётся один раз на старте, см. `SessionQuestionRepository`) и сохраняется в новой колонке `session_questions.question_type` (nullable, `NULL` = `FORM_BY_CASE`, как и в JSON-контракте §2.1). Повторный вызов `resume` не должен пере-рандомизировать тип — читается сохранённое значение через `SessionQuestionToDtoMapper`.

**Не путать с распределением itemType/vowel_type в самой сессии** — это отдельный, уже существующий механизм отбора (`quiz-generator-spec.md` §3–4), он не меняется.

**Открытый вопрос:** веса 0.5/0.3/0.2 — стартовое значение без A/B-данных, менять по фидбеку без ревизии контракта (это внутренняя константа content-service, не часть OpenAPI).

## 5. «Все основы» — сквозной (кросс-lesson) квиз по всем гласным основам

**Статус: ЧЕРНОВИК.** Поставлено Агентом 0 (декомпозиция), контракт — Агентом 6, реализация — Агентами 2/3.

### 5.1. Назначение

Отдельный пункт меню «Грамматика → Существительные → Все основы» — универсальный квиз, объединяющий стемы
сразу из всех существующих уроков склонения гласных основ (`declensions-a-masc`, `declensions-aa-fem`,
`declensions-i-u`, `declensions-ii-uu`, `declensions-r`), без привязки к одному уроку. Парадигмы/таблицы
склонений (`GrammarParadigmTable`, см. `frontend/pages/grammar-lesson-page.md` §2.2) на этой странице **не
показываются** — сознательное ограничение по требованию заказчика, а не пропуск.

### 5.2. Виртуальный урок `declensions-all`

Новая строка `content.quizzes`: `slug = "declensions-all"`, `lessonType = DECLENSIONS`, `titleRu = "Все
основы"`, `titleEn = "All stems"`. В отличие от прочих `DECLENSIONS`-уроков эта строка не связана с одним
`vowelType`/`gender` — её `declension_stems` не фильтруются по `lesson_id`. Пул стемов для генерации
вопросов при `slug = declensions-all` строится прямым запросом к `content.declension_stems` по значениям
`filterVowelTypes`/`filterGenders` (без условия на `lesson_id`) — реализация и её постфактум-документирование
(вариант хранения: игнорировать `lesson_id` для этого конкретного slug, отдельная таблица-агрегатор не
заводится) — на усмотрение Агента 2, зафиксировать выбор в этом разделе после реализации.

### 5.3. Фильтры UI и контракт `filterScope=ALL_STEMS`

Три независимых мульти-выбора (без вкладок и без таблиц парадигм/прогресса — см. §5.1):

- **По гласным основ** — множественный выбор из `vowelType`: A_STEM, AA_STEM, I_STEM, II_STEM, U_STEM,
  UU_STEM, R_STEM (только 7 значений, для которых сейчас есть сидированные данные — местоименные
  `PRON_*` и согласные основы в этот фильтр не включаются, пока по ним нет уроков/данных).
- **По числам** — множественный выбор из `numberType`: SINGULAR, DUAL, PLURAL.
- **По родам** — множественный выбор из `gender`: MASCULINE, FEMININE, NEUTER, UNSPECIFIED. Для
  I_STEM/II_STEM/U_STEM/UU_STEM/R_STEM (ADR-005) реально существует только `UNSPECIFIED` — если
  пользователь выбрал вместе одну из этих гласных и род MASCULINE/FEMININE/NEUTER, соответствующая
  комбинация просто не даёт вопросов (не ошибка, см. §5.4).

Пустой выбор на любой из трёх осей = «все значения этой оси», как и в существующих `filterScope`
(§3.4) — контракт единообразен: `filterScope=ALL_STEMS` использует `filterVowelTypes`/`filterGenders`/
`filterNumberTypes` (`parameters.yaml#FilterVowelTypesParam`/`FilterGendersParam`/`FilterNumberTypesParam`),
`filterCaseTypes`/`filterCombinations` при этом scope игнорируются. Падежи (`caseType`) фильтром не
охватываются — в квиз всегда входят все 8 падежей для отобранных гласных/чисел/родов (это единственная
ось, которую страница «Все основы» не фильтрует, по требованию заказчика в этой итерации).

### 5.4. Кнопка «Начать квиз»

Кнопка одна, без вкладок и без live-счётчика N в этой итерации (в отличие от §3.3 — там N считается по
уже загруженной таблице прогресса конкретного урока; здесь такой таблицы нет, а честный подсчёт N
потребовал бы отдельного `count`-запроса к content-service — вынесено в открытые вопросы, см. ниже).
Клик по кнопке вызывает тот же `POST /quiz/declensions-all/sessions/start-or-resume` (см.
`quiz-sessions.yaml`) с `filterScope=ALL_STEMS` и текущими значениями трёх фильтров. Резюм
незавершённой сессии — по равенству `filterScope=ALL_STEMS` + совпадению множеств `filterVowelTypes`/
`filterGenders`/`filterNumberTypes` (без учёта порядка), тот же механизм, что и в §3.4.

Если отобранная комбинация гласных×родов×чисел не даёт ни одного вопроса (см. пример в §5.3 про
несуществующие пары гласная/род) — бэкенд отвечает `SCOPE_FILTER_EMPTY` (тот же код ошибки, что и в §3.4),
фронтенд показывает то же сообщение об ошибке, что и для обычных уроков склонения.

### 5.5. Рендеринг вопросов

Без изменений относительно §4 — `questionType` (FORM_BY_CASE/CASE_BY_FORM/ENDING_MATCH) назначается
content-service тем же алгоритмом §4.5, независимо от того, что стемы вопроса взяты из разных исходных
уроков. Ограничение: ENDING_MATCH сравнивает окончания только внутри одного `vowelType` (см. §4.3) — при
широком выборе нескольких гласных в фильтре пул кандидатов на дистракторы для ENDING_MATCH всё равно
строится отдельно на каждый вопрос по его собственному `vowelType`, а не по всем выбранным гласным сразу.
