# Задача: frontend — интеграция QuestionRenderer в страницу прохождения квиза

**Что:** Подключить `QuestionRenderer` (task-frontend-01) в существующий контейнер сессии
квиза, обновить хук отправки ответа под новый payload (`MatchingAnswerPayload` для MATCHING,
обычная строка для остальных).
**Зачем:** См. `docs/frontend/frontend-state.md` §6 (API-хуки), §5а (типы).

## Зависит от
task-frontend-01-question-renderers.md

## Шаги

1. Найти существующий хук `useSubmitAnswer` (`docs/frontend/frontend-state.md` §6, `hooks/useQuizzes.ts`) — расширить сигнатуру мутации: `mutationFn: (payload: AnswerPayload | MatchingAnswerPayload) => ...`, на бэкенде решает `answerMode` текущего вопроса, какой JSON-контракт ожидать (см. `quiz-service` API — сверить фактический контракт эндпоинта submit-answer в `docs/services/quest-engine.md`, при необходимости завести отдельный метод `quizApi.submitMatchingAnswer` вместо перегрузки одного метода — на усмотрение реализации, лишь бы вызывающий код (`QuestionRenderer`) не знал деталей HTTP-контракта).
2. В контейнере сессии (странице `/quiz/grammar/:type`, см. предупреждение в task-frontend-01 про поиск актуального компонента) — заменить прямой рендер варианта вопроса (сейчас, судя по типам в `frontend-state.md`, скорее всего жёстко подразумевается один тип — выбор из `options`) на `<QuestionRenderer question={currentQuestion} onSubmit={handleSubmit} />`.
3. `handleSubmit` — единая точка: собирает нужный payload (используя `question.id`, `sessionId` из состояния страницы) и вызывает `useSubmitAnswer().mutate(...)`, дальше — существующая логика показа `AnswerResult` и перехода к следующему вопросу не меняется.
4. Прогресс-бар/счётчик «Вопрос N из M» (`quiz.question` ключ i18n, уже существует) — не требует изменений, `SessionQuestion[]` как массив не меняет форму (только элементы получили новые поля).
5. Ручная проверка (или e2e/Cypress-тест, если такие есть в проекте): пройти сессию, где вперемешку идут вопросы всех 4 `answerMode` — от старта сессии до экрана результатов без ошибок в консоли и без зависаний UI между вопросами разных типов.

## Критерии готовности (DoD)
- [ ] Сессия с вопросами всех 4 типов подряд проходится без ошибок в консоли браузера
- [ ] После ответа на MATCHING-вопрос показывается результат, после чего кнопка «Следующий вопрос» ведёт к следующему вопросу как обычно (не зависает на MATCHING-специфичном состоянии)
- [ ] `useSubmitAnswer`/аналог не требует от `QuestionRenderer` знания HTTP-путей — вызывающий код передаёт только доменные данные (id вопроса, ответ)
