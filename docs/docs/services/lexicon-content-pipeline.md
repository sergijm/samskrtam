# Lexicon Content Pipeline — наполнение ~2000 базовых лемм

> Связанные файлы: [lexicon.md](./lexicon.md), [lexical-curriculum.md](./lexical-curriculum.md),
> [dictionary-service.md](./dictionary-service.md) (один из источников enrichment).

---

## 1. Source data — откуда берём сырьё

Кандидаты на 2000 лемм (приоритет по частотности, не по алфавиту — сначала
заполняются `CORE`/`ESSENTIAL` полосы, см. `lexical-curriculum.md` §2):

| Поле | Источник | Комментарий |
|---|---|---|
| `lemmaIast`/`lemmaDevanagari` | Существующие открытые частотные списки санскритской лексики (учебные, например по корпусу DCS — Digital Corpus of Sanskrit) + `content.vocabulary_words` (уже собранные ~ слова из sangraha-текстов, как стартовый пласт) | Не придумывается вручную — берётся из существующих корпусных данных |
| `frequencyRank` | Тот же корпусный источник, `lexicon.lexeme_frequency.source = 'CURATED_2000'` | Собственный ранжированный список проекта, а не сырой ранк из внешнего корпуса один-в-один — корпусный ранк может включать словоформы/имена собственные, которые для учебных целей фильтруются вручную на этапе review (§3) |
| `meaning` (`glossRu`/`glossEn`) | Monier-Williams (через `dictionary-service`, см. `lexicon.md` §0 п.1) для EN-based первичного значения; RU — либо существующие переводы в `content.vocabulary_words`, либо AI-enrichment (§2) с последующей проверкой | MW-статья часто длинная — `glossEn` формируется как краткая выжимка (первые 1–2 значения), не копия статьи целиком |
| `pos`, `gender` | MW (частично структурировано), уточняется AI-enrichment | MW не всегда даёт машиночитаемый POS — нужен разбор/AI |
| `morphology` (стем-класс/verb-класс) | Выводится правилами по форме леммы (например, лемма на `-a` мужского рода → кандидат `a-stem-masc`, требует подтверждения) + AI-enrichment для нестандартных случаев | Не 100% автоматизируемо — часть требует ручной проверки (§3) |
| `Source` occurrences | Существующие данные sangraha-service (уже распарсенные стихи) — переиспользуются, не парсятся заново | См. `lexicon.md` §0 п.2 |

## 2. Enrichment — AI-assisted workflow

Raw lexeme (лемма + сырой ранк, без значения/POS/темы)
→ **AI enrichment** (LLM-запрос с фиксированным промптом, structured output):
предлагает `glossRu`/`glossEn` (кратко, ≤300 символов), `posCodes[]`,
`semanticTopicIds[]` (выбор из уже существующего дерева §3
`lexical-curriculum.md`, **не** придумывание новых категорий моделью),
`morphologyClassCodes[]`, `gender`
→ **Structured candidate** (строка `lexicon.lexeme` со `status = AI_ENRICHED`,
плюс черновые связи в таксономических M:N-таблицах, тоже помеченные как
неподтверждённые — см. §3 про флаг подтверждения)
→ **Validation** (правила, §3)
→ **Human/rule review** (ADMIN просматривает очередь `AI_ENRICHED`, подтверждает
или правит через `LexemeController`/`LexemeTaxonomyController`,
`task-curriculum-10-lexicon-admin-crud.md`)
→ **Approved lexeme** (`status = APPROVED`) — только эти лексемы попадают в
`pool/resolve` по умолчанию для обычных (не превью/не ADMIN) quiz-сессий; фильтр
по `status = APPROVED` — жёсткое условие в `LexemePoolService`, не опциональное.

**AI не единственный источник истины** (задача §20, явное требование):
- предложенные `semanticTopicId` ограничены существующим деревом (LLM не может
  создать новую категорию через этот пайплайн — создание категорий отдельная
  ручная ADMIN-операция, редкая);
- ни одна AI-enriched строка не достигает `pool/resolve` без прохождения
  `APPROVED` — то есть у пайплайна есть обязательный человеческий gate, не
  softgate типа «можно пропустить, если модель уверена».

## 3. Validation — что проверяем перед APPROVED

| Проверка | Правило | Действие при нарушении |
|---|---|---|
| Дубликаты | `UNIQUE(lemmaSlp1, gender)` на уровне БД + предварительный fuzzy-check (Levenshtein по `lemmaSlp1` < 2 на этапе импорта, до insert) | Insert отклоняется констрейнтом; fuzzy-совпадения — в очередь ручного review, не автоматическое слияние |
| Неправильная лемма | Проверка, что `lemmaIast`/`lemmaDevanagari` — словарная форма (для существительных — Nom.Sg. или основа, не случайная словоформа), сверка с MW/DCS написанием | Флаг `needsReview` (доп. поле, не описанное в §1 `lexicon.md` как отдельная колонка — реализуется как временное значение `status = DRAFT` с комментарием в admin UI, не отдельная сущность) |
| Транслитерация | Автоматическая сверка `lemmaIast` ↔ `lemmaDevanagari` через существующий IAST↔Devanāgarī конвертер проекта (если есть в shared-модуле, иначе — тривиальная таблица соответствий, тот же принцип, что использует `dictionary-service`/content-service для транслитерации) | Несовпадение — блокирует `APPROVED`, обязательный человеческий фикс |
| POS | Сверка предложенного AI `posCode` с MW-пометой части речи (если есть в исходной статье) | Расхождение — не блокирует, но помечается для приоритетного review |
| Gender | Для `NOMINAL` POS — `gender` обязателен (`NOT NULL` на уровне бизнес-правила, хотя колонка технически nullable для неименных POS); отсутствие — блокирует `APPROVED` | — |
| Связь с Topic | Проверка на этапе формирования `lexical_topic_binding` (§1 `lexical-curriculum.md`): каждая целевая Topic после наполнения должна иметь ≥ 10 лексем (иначе — сигнал на объединение тем, см. `lexical-curriculum.md` §3 про минимальный размер категории) | Отчёт "Topics below threshold" в admin UI, не автоблокировка |
| Ошибки frequency ranking | Сверка кумулятивного покрытия: топ-100 по `rank` должны совпадать (по множеству, не по точному порядку) с общепризнанным списком служебных/базовых слов санскрита (ручной чеклист на этапе первичной загрузки, не автоматизируется полностью) | Ручная корректировка `rank` до первого `APPROVED`-прохода по батчу |

## 4. Seed plan — порядок наполнения 2000 слов

Наполнение батчами по 200 лемм, в порядке `frequencyRank` (не по темам — тема у
слова часто определяется уже после того, как оно попало в батч по частотности):

| Батч | rank диапазон | Ожидаемый охват тем (`lexical-curriculum.md` §6) | Оценка трудозатрат review |
|---|---|---|---|
| 1 | 1–200 | L0 целиком + начало L1 (function words, базовые глаголы/местоимения/числительные) | Высокий приоритет ручной проверки (это ядро, ошибки здесь дороже всего) |
| 2 | 201–400 | Остаток L1 (Animals, Food, House, Colors, базовые прилагательные) | Средний |
| 3 | 401–600 | L2 (Weather, Time, Occupations, Travel, Materials) | Средний |
| 4 | 601–900 | L3 начало (Emotions, Character, Social relations) | Средний |
| 5 | 901–1200 | L3 остаток + L4 начало (Ritual, Ethics, Knowledge) | Ниже (более узкая, специализированная лексика — AI enrichment точнее на предметной лексике, чем на многозначных базовых словах) |
| 6 | 1201–1500 | L4 остаток + L5 начало (War, Music, Mythology/epithets) | Ниже |
| 7 | 1501–2000 | L5 остаток + L6 (морфологически ориентированные подборки — здесь возможен добор из уже загруженных 1–1500, не обязательно новые леммы) | Ниже |

**После каждого батча:** пересчёт `SourceOccurrence`-кэшей (§4 `lexicon.md`,
если батч пересекается с уже распарсенными sangraha-текстами), проверка порога
по Topic (§3 таблица выше), обновление `lexical_topic_binding` для
затронутых Lexical Topics.

**Иллюстративный пример (не полный список — 2000 строк не публикуются в
документации, только в БД/CSV-выгрузке пайплайна):** первые строки батча 1,
демонстрирующие формат данных, приведены в `V4__seed_sample_lexemes.sql`
(services/curriculum-service/…/db/migration) — 25 реальных высокочастотных
лемм (служебные слова, базовые местоимения/числительные/глаголы) как proof-of-
concept формата загрузки, не как замена полного batch-пайплайна.

## 5. Открытые вопросы

- Точный источник корпусной частотности (DCS export vs собственный подсчёт по
  уже загруженным sangraha-текстам) — решение о конкретном источнике `rank` для
  `source = 'CURATED_2000'` принимается при реализации, не в этом документе;
  скорее всего — гибрид (корпусный ранк как стартовая точка, ручная коррекция
  топ-200 по педагогическому здравому смыслу, см. §3 таблица).
- Омонимы с одинаковым `gender`, но разным значением — в этой версии **не
  разделяются** на разные `Lexeme` (см. `lexicon.md` §1) — если в процессе
  наполнения 2000 слов такие случаи окажутся частыми и педагогически значимыми,
  потребуется either расширение уникальности (например, добавить
  `senseNumber`), либо явный отказ от объединения — решение по факту
  накопленных данных, не заранее.
- Формат промпта AI-enrichment (§2) — конкретный текст промпта, few-shot
  примеры и модель — вопрос реализации агента, не архитектуры; здесь
  зафиксирован только контракт (структура выхода, обязательный human gate).
